# 自托管：把服务搬回自己手里

> 云服务给你一个域名就能用。自托管给你的是控制权，代价是你得自己当运维。

## 先说清楚不划算的部分

自托管最常被推销成「省钱」，但这只是账面的另一半。按一台家用机器三年折旧、电费、硬盘更换、你的时间算：

| 项目 | 云服务 | 自托管 |
| --- | --- | --- |
| 初始投入 | 几分钟 | 一整个周末 |
| 月度成本 | 按用量付费，通常有免费额度 | 电费 + 域名 + 硬盘折旧 |
| 停机责任 | 平台负责 | 你负责 |
| 数据归属 | 在别人手里 | 在你手里 |
| 扩容 | 点一下 | 换机器、搬数据 |
| 维护升级 | 平台推送 | 你决定什么时候升 |

**结论不是「自托管更好」，而是它把成本从「钱」换成了「你的注意力」。** 如果一台机器要跑十几个服务、还要对外网开放，那你换来的不只是省钱，还有半夜被证书过期叫醒的风险。

## 一台机器现实能承担多少

家用网络的上行带宽通常是下行的一个零头，这是自托管最先撞到的墙。

```
上行 20 Mbps  ≈  理论上限 2.5 MB/s  ≈  一张原图约 4 秒
```

所以判断值不值得做，只问一句：**这些服务的使用者是「你自己和家里人」，还是「任何人都能访问」？** 前者随便做，后者要先算上行和备案。

| 服务类型 | 外网访问可行性 | 说明 |
| --- | --- | --- |
| 文档、相册、影音库 | 可行，需上行足够 | 图片小、视频流可以限码率 |
| 代码仓库、CI | 可行 | 负载小，但安全更新要及时 |
| 大文件网盘 | 不建议 | 上下行不对称会很难受 |
| 对话式服务 | 一般 | 实时性强，延迟直接影响体验 |

## 三种典型架构

不要一上来就上 Kubernetes。家用环境里，下面三种覆盖了 95% 的需求。

### 方案一：裸机直装

直接在系统上装服务，用 systemd 托管。

- 优点：性能最好，链路最短，排障时没有中间层
- 缺点：依赖管理靠人，升级要一个个来
- 适合：只有一两个服务，且你熟悉 Linux

### 方案二：Docker 容器（本文默认）

每个服务跑在独立容器里，共享宿主机内核。

- 优点：环境隔离、启停一致、迁移容易
- 缺点：多一层网络和存储抽象，报错信息会变长
- 适合：服务数量在三个以上

### 方案三：虚拟机 / LXC

每个服务一个完整系统。

- 优点：隔离最彻底，内核也能隔离
- 缺点：内存开销大，跨系统传文件麻烦
- 适合：需要跑不同内核、或要跑不受信任的代码

::: tip 选型建议
先用方案二。绝大多数「跑不起来」的问题，根源不是隔离不够，而是权限和数据路径没搞对 —— 换更重的方案只会让问题更难查。
:::

## 一台机器的四条边界

在动手之前，先把这四条想清楚，能省掉后面 80% 的返工。

| 边界 | 问题 | 建议 |
| --- | --- | --- |
| 电力 | 停电后能不能自恢复 | 主板支持的话开启来电自启动 |
| 网络 | 家庭宽带有没有公网 IP、是否被墙 | 先用内网穿透，别直接开端口 |
| 存储 | 备份放在哪 | 规则：备份不能和数据在同一台机器 |
| 安全 | 谁在访问 | 先只开内网，确认好用再暴露 |

**备份这条值得重复一遍：备份和数据放在同一台机器上，等于没有备份。** 至少要有一份在异地。

## 你的路怎么走

**装起来** —— 第 1 章装好 Docker 引擎，跑通第一个容器，确认这条链路在你的机器上是通的。

**管得住** —— 第 2 章把所有服务收进一份 Compose 文件，从此更新、备份、升级都有固定动作，不再是「登录进去挨个敲」。

**场景篇** —— 每次只加一个场景，跑通到能看见结果为止。一次上五个服务，出问题时你分不清是谁的锅。

**拆原理** —— 出过几次故障之后再看。你会发现自己想问的问题变了：从「这条命令什么意思」变成「这个挂载为什么没写进去」。
